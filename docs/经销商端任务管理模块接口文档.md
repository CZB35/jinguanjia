# 经销商端任务管理模块接口文档

本文档用于经销商端“任务管理”大模块联调，覆盖任务列表、任务创建、任务详情、进度追踪、分配师傅、重新分派、附件、实据、关闭任务、任务日志、经销商评价等页面和操作。

## 1. 基础说明

接口基地址：

```text
https://goldenbutler.friendchenkeji.cn/api
```

鉴权请求头：

```http
Authorization: Bearer <access_token>
```

JSON 请求头：

```http
Content-Type: application/json
```

文件上传请求头：

```http
Content-Type: multipart/form-data
```

统一响应结构：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "xxxx"
}
```

经销商端数据范围：

1. 经销商只能看到自己所属门店的任务。
2. 经销商只能选择自己所属门店下的师傅。
3. 经销商账号按单门店绑定，当前门店建议从 `GET /me/profile` 的 `store_id` 读取。

## 2. 服务环节枚举

| 值 | 中文 |
| --- | --- |
| `measure` | 量尺 |
| `install` | 安装 |
| `ironing` | 熨烫 |
| `cleaning` | 除尘除螨 |

## 3. 任务状态和按钮规则

页面上“待执行”会对应两个内部状态，前端必须用 `task_status` 区分。

| `task_status` | `task_status_text` | `display_status_text` | 页面操作 |
| --- | --- | --- | --- |
| `pending_assign` | 待分配 | 待执行 | 显示“分配师傅” |
| `pending_execute` | 待执行 | 待执行 | 显示“重新分派” |
| `executing` | 进行中 | 进行中 | 可显示“重新分派” |
| `pending_dealer_review` | 待评价 | 待评价 | 显示“去评价” |
| `pending_hq_score` | 待评分 | 待评价 | 不显示分配或评价按钮 |
| `completed` | 已完成 | 已完成 | 不显示分配或评价按钮 |
| `closed` | 已关闭 | 已完成 | 不显示分配或评价按钮 |

列表页按钮判断：

| 判断条件 | 按钮 |
| --- | --- |
| `task_status === 'pending_assign'` | 分配师傅 |
| `task_status === 'pending_execute'` | 重新分派 |
| `task_status === 'executing'` | 重新分派，是否展示由产品决定，后端当前允许 |
| `task_status === 'pending_dealer_review'` | 去评价 |

详情页按钮判断：

| 字段 | 说明 |
| --- | --- |
| `can_assign` | `true` 时显示“分配师傅” |
| `can_reassign` | `true` 时显示“重新分派” |
| `can_submit_review` | `true` 时显示“去评价” |
| `can_contact_customer` | `true` 时可显示“联系客户” |

注意：`GET /tasks` 列表当前不返回 `can_assign/can_reassign`，列表页请按 `task_status` 推导；`GET /tasks/{id}` 详情会返回 `can_assign/can_reassign/can_submit_review`。

## 4. 推荐页面流程

任务列表页：

1. 调用 `GET /tasks` 获取任务列表。
2. 使用 `display_status_text` 展示状态文案。
3. 使用 `task_status` 判断显示“分配师傅”还是“重新分派”。

任务详情页：

1. 调用 `GET /tasks/{id}` 获取完整详情。
2. 用 `progress_tracks` 渲染进度追踪。
3. 用 `can_assign/can_reassign/can_submit_review` 控制操作按钮。
4. 用 `service_items` 渲染多服务环节。

分配师傅页：

1. 调用 `GET /tasks/{id}` 获取 `store.id` 和 `service_items`。
2. 单服务环节调用 `GET /technicians/available`。
3. 多服务环节调用 `GET /technicians/available/grouped`。
4. 未分配任务调用 `POST /tasks/{id}/assign`。
5. 已分配待执行任务调用 `POST /tasks/{id}/reassign`。

## 7. 创建任务

- 接口：`POST /tasks`
- 用途：经销商端新建任务

说明：

1. 后端会按手机号查找或创建客户，不要求前端先调用 `POST /customers`。
2. 经销商未传 `store_id` 时，后端会使用当前经销商所属门店。
3. `service_types` 是多服务环节推荐字段。
4. `service_type` 是旧单环节兼容字段。
5. `address` 推荐传对象，也兼容直接传字符串；字符串会作为详细地址保存。

请求字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `customer_name` | string | 是 | 客户姓名 |
| `customer_mobile` | string | 是 | 客户手机号 |
| `customer_source` | string | 否 | 客户来源 |
| `store_id` | number | 否 | 门店 ID，经销商可不传 |
| `address_id` | number | 否 | 已有地址 ID |
| `address.province` | string | 否 | 省 |
| `address.city` | string | 否 | 市 |
| `address.district` | string | 否 | 区 |
| `address.detail` | string | 条件必填 | 新地址详情，未传 `address_id` 时必填 |
| `address` | string | 否 | 兼容写法，直接作为详细地址保存 |
| `service_type` | string | 条件必填 | 单服务环节，和 `service_types` 二选一 |
| `service_types` | string[] | 条件必填 | 多服务环节，和 `service_type` 二选一 |
| `appointment_time` | string | 是 | 预约时间，格式 `YYYY-MM-DD HH:mm:ss` |
| `service_time_slot` | string | 否 | 服务时段 |
| `priority` | string | 否 | 优先级，`low/normal/high` |
| `task_desc` | string | 否 | 任务描述 |
| `task_remark` | string | 否 | 备注 |

请求示例：

```json
{
  "customer_name": "张三",
  "customer_mobile": "13800000000",
  "customer_source": "线下门店",
  "service_types": ["install", "ironing"],
  "appointment_time": "2026-04-29 14:00:00",
  "service_time_slot": "下午",
  "priority": "normal",
  "address": {
    "province": "浙江省",
    "city": "杭州市",
    "district": "西湖区",
    "detail": "文一路 123 号"
  },
  "task_desc": "窗帘安装和熨烫",
  "task_remark": "客户下午在家"
}
```

兼容字符串地址示例：

```json
{
  "customer_name": "森屿",
  "customer_mobile": "17796854338",
  "service_types": ["measure", "install", "ironing", "cleaning"],
  "appointment_time": "2026-06-17 21:57:00",
  "service_time_slot": "晚上",
  "priority": "normal",
  "store_id": 1,
  "address": "北京市东城区南京详情地址",
  "task_desc": "任务描述",
  "task_remark": ""
}
```

成功返回：

```json
{
  "id": 1001,
  "task_no": "RW20260429140000123",

    {
```

## 9. 任务详情进度追踪

进度追踪请优先使用 `progress_tracks` 渲染，不要自己在前端拼节点。

`progress_tracks` 节点结构：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `key` | string | 节点编码：`created/assigned/photos/completed` |
| `title` | string | 节点标题 |
| `finished` | boolean | 是否完成 |
| `time` | string | 节点时间，未完成时为空 |
| `expected_time` | string | 预计时间，当前用于完成环节展示预约时间 |
| `service_type` | string | 关联服务环节 |
| `technician_id` | number | 关联师傅 ID |
| `technician_name` | string | 关联师傅姓名 |
| `images` | array | 节点图片，当前用于现场照片节点 |

`progress_tracks[].images` 图片字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 图片 ID |
| `file_name` | string | 文件名 |
| `file_url` | string | 可直接访问的 `/uploads/...` 路径 |

当前节点顺序：

| 顺序 | 节点标题 | 点亮规则 | 时间来源 |
| --- | --- | --- | --- |
| 1 | 任务创建 | 固定点亮 | `task.created_at` |
| 2 | 已分派给{师傅名} | 存在分派记录 | 最早 `assignments[].assigned_at` |
| 3 | 现场照片 | 存在图片实据 | 最早图片 `shot_at/created_at` |
| 4 | 完成{服务环节} | 所有环节进入待评价、待评分、已完成或已关闭 | 环节完成时间或最新 `executions[].submitted_at` |

完成环节时间展示：

1. 已完成时使用 `time`。
2. 未完成时可以展示 `expected_time`，即预约时间。
3. 前端可显示为“预计 16:30”这类文案。

进度百分比说明：

| 状态 | 进度 |
| --- | --- |
| `pending_assign` | 0 |
| `pending_execute` | 0 |
| `executing` | 60 |
| `pending_dealer_review` | 90 |
| `pending_hq_score` | 95，若存在多环节子项则按子项平均，通常仍为 90 |
| `completed` | 100 |
| `closed` | 100 |

前端展示建议：

1. 顶部状态用 `display_status_text`。
2. 任务明细状态判断用 `task_status`。
3. 进度条百分比用 `progress_percent`。
4. 时间轴节点用 `progress_tracks`。
5. 多环节展示用 `service_items` 和 `service_items_text`。
6. 当前不返回“到达现场”节点，前端不要自行补这个节点。

## 10. 可用师傅列表

- 接口：`GET /technicians/available`
- 用途：单个服务环节选择可分配师傅

查询参数：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `store_id` | number | 是 | 任务所属门店 ID |
| `service_type` | string | 是 | 服务环节 |

请求示例：

```http
GET /api/technicians/available?store_id=3&service_type=install
```

过滤规则：

1. 只返回当前门店下的启用师傅。
2. 只返回 `service_types` 包含当前 `service_type` 的师傅。
3. 经销商只能查询自己所属门店的师傅。

返回师傅字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 师傅 ID |
| `name` | string | 姓名 |
| `nickname` | string | 昵称 |
| `mobile` | string | 手机号 |
| `avatar_url` | string | 头像 |
| `job_no` | string | 工号 |
| `status` | string | 状态 |
| `role_names` | string[] | 角色名称 |
| `store_names` | string[] | 所属门店 |
| `work_status` | string | 工作状态 |
| `service_types` | string[] | 服务能力 |
| `average_score` | number | 平均评分 |
| `completed_order_count` | number | 已完成单量 |
| `pending_order_count` | number | 待完成单量 |
| `current_task_no` | string | 当前任务号 |
| `current_task_status` | string | 当前任务状态 |

## 11. 多服务环节可用师傅分组

- 接口：`GET /technicians/available/grouped`
- 用途：多服务环节任务一次性返回各环节可用师傅

查询参数：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `store_id` | number | 是 | 任务所属门店 ID |
| `service_types` | string | 是 | 多个服务环节，英文逗号拼接 |

请求示例：

```http
GET /api/technicians/available/grouped?store_id=3&service_types=install,ironing
```

返回示例：

```json
{
  "groups": [
    {
      "service_type": "install",
      "service_type_text": "安装服务",
      "technicians": []
    },
    {
      "service_type": "ironing",
      "service_type_text": "熨烫服务",
      "technicians": []
    }
  ]
}
```

说明：

1. 每个 `groups[].technicians` 都只包含具备该 `service_type` 能力的师傅。
2. 多环节分配页建议优先使用此接口，避免前端循环请求。
3. 某个服务环节没有师傅时，该组 `technicians` 返回空数组。

## 12. 分配师傅

- 接口：`POST /tasks/{id}/assign`
- 适用状态：`pending_assign`
- 页面按钮：分配师傅

整单分配给同一个师傅：

```json
{
  "technician_id": 28,
  "assign_reason": "任务分配"
}
```

单环节按 `service_type` 分配：

```json
{
  "service_type": "install",
  "technician_id": 28,
  "assign_reason": "安装环节分配"
}
```

单环节按 `service_item_id` 分配：

```json
{
  "service_item_id": 101,
  "technician_id": 28,
  "assign_reason": "安装环节分配"
}
```

多环节批量分配：

```json
{
  "assignments": [
    { "service_type": "install", "technician_id": 28 },
    { "service_type": "ironing", "technician_id": 29 }
  ],
  "assign_reason": "任务分配"
}
```

多环节按 `service_item_id` 批量分配：

```json
{
  "assignments": [
    { "service_item_id": 101, "technician_id": 28 },
    { "service_item_id": 102, "technician_id": 29 }
  ],
  "assign_reason": "任务分配"
}
```

成功返回：

```json
{
  "task_id": 1001,
  "task_status": "pending_execute"
}
```

分配规则：

1. 指定的 `service_type` 或 `service_item_id` 必须属于当前任务。
2. 师傅必须属于当前任务门店。
3. 师傅 `service_types` 必须包含对应服务环节。
4. 整单分配时，所选师傅必须具备当前任务全部服务环节能力。
5. 只分配部分服务环节时，任务仍保持 `pending_assign`。
6. 所有服务环节都分配后，任务状态变为 `pending_execute`。
7. 同一个师傅被分配同一任务的多个服务环节时，师傅端会按服务环节收到多条任务卡片。

## 13. 重新分派师傅

- 接口：`POST /tasks/{id}/reassign`
- 适用状态：`pending_execute`、`executing`
- 页面按钮：重新分派

整单修改任务类型并重新分派示例：

```json
{
  "technician_id": 29,
  "service_type": "install",
  "assign_reason": "任务资料调整后重新分派",
  "customer_name": "张三",
  "customer_mobile": "13800000000",
  "appointment_time": "2026-07-18 14:30:00",
  "service_time_slot": "下午",
  "address": {
    "province": "浙江省",
    "city": "杭州市",
    "district": "西湖区",
    "detail": "文一路 123 号"
  },
  "priority": "normal",
  "task_desc": "更新后的任务描述",
  "task_remark": "更新后的备注"
}
```

`technician_id` 为整单/单环节条件必填，`assign_reason` 可选且默认“重新分派”。整单重派时可选传
`service_type` 修改当前任务本身，并可同时传
`customer_name`、`customer_mobile`、`customer_source`、`address_id/address`、
`appointment_time`、`service_time_slot`、`priority`、`task_desc`、`task_remark`。
这些字段会与重派记录在同一事务中保存；未传字段保持原值。接口同时兼容对应的驼峰字段，
以及详情接口返回的 `customer.name/customer.mobile/customer.address` 嵌套结构。

修改预约时间时，后端会同步服务环节的 `scheduled_time`。同时传旧 `address_id` 和新
`address` 时以新地址为准，新地址只绑定当前任务，不覆盖历史地址记录。
客户姓名、手机号和来源属于共享客户资料，修改后该客户的其他历史任务也会展示新资料。

单环节重派必须使用详情返回的 `service_item_id`：

```json
{
  "service_item_id": 101,
  "technician_id": 29,
  "assign_reason": "安装环节更换师傅"
}
```

批量重派使用 `assignments`，每一项都必须有 `service_item_id`；批量模式省略顶层 `technician_id/service_item_id/service_type`。

成功返回：

```json
{
  "task_id": 1001,
  "task_status": "pending_execute",
  "service_item_id": null,
  "service_type": "install",
  "execution_id": null
}
```

重派规则：

1. 顶层 `service_type` 不参与环节定位；不带 `service_item_id/assignments` 时表示整单的新任务类型。
2. 当前任务状态必须是 `pending_execute` 或 `executing`。
3. 可以重新派发给当前师傅，用于任务资料修改后重新通知。
4. 任一服务环节已提交检核、待评价或已完成后不允许整单重派。
5. 新师傅必须属于当前任务门店。
6. 传新 `service_type` 时按新类型校验师傅能力；未传时校验当前全部环节能力。
7. 修改类型要求任务恰好有一个服务环节，并同步更新主任务和该环节；同组已有目标类型时返回 409。
8. 单环节和批量重派必须传 `service_item_id`，不能只传类型。
9. 进行中的旧执行记录会在重派事务内取消，旧 `execution_id` 不能继续提交；旧照片保留为历史但不计入当前进度。

## 14. 关闭任务

- 接口：`POST /tasks/{id}/close`
- 用途：关闭异常或不再执行的任务

请求示例：

```json
{
  "close_reason": "客户取消服务"
}
```

成功返回：

```json
{
  "task_id": 1001,
  "task_status": "closed"
}
```

说明：

1. `close_reason` 必填。

## 16. 经销商评价

- 接口：`POST /tasks/{id}/dealer-review`
- 适用状态：当前服务环节 `pending_dealer_review`
- 页面按钮：去评价

请求字段：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `service_item_id` | number | 推荐 | 服务环节子项 ID，来自任务列表项或详情 `service_items[].id` |
| `service_type` | string | 否 | 未传 `service_item_id` 时可用服务环节编码兜底 |
| `star` | number | 是 | 星级，范围 `1-5` |
| `tags` | string[] | 否 | 评价标签 |
| `content` | string | 否 | 评价内容 |

请求示例：

```json
{
  "service_item_id": 101,
  "star": 5,
  "tags": ["准时", "服务好"],
  "content": "师傅服务很好"
}
```

成功返回：

```json
{
  "task_id": 1001,
  "task_status": "pending_dealer_review",
  "service_item_id": 101,
  "service_type": "install"
}
```

说明：

1. 经销商只能评价自己所属门店任务。
2. 同一个服务环节不能重复评价；同一任务多个服务环节需要分别评价。
3. 单个环节评价后，该环节进入 `pending_hq_score`；如果还有其他环节待评价，任务主状态保持 `pending_dealer_review`。
4. 所有服务环节都评价后，任务主状态才进入 `pending_hq_score`。

## 20. 常见错误

| 场景 | 可能状态码 | 说明 |
| --- | --- | --- |
| 未登录或 token 失效 | `401` | 重新登录 |
| 操作非所属门店任务 | `403` | 经销商越权 |
| 任务不存在 | `404` | ID 错误或任务已删除 |
| 当前任务状态不允许分派 | `409` | 不是 `pending_assign` |
| 当前任务状态不允许重派 | `409` | 不是 `pending_execute/executing` |
| 师傅不属于当前门店 | `409` | 需要选择任务门店下师傅 |
| 师傅不具备服务能力 | `409` | 需要按 `service_type` 过滤可用师傅 |
| 评价星级不合法 | `400` | `star` 必须为 `1-5` |
| 重复评价 | `409` | 同一任务不能重复评价 |

错误响应示例：

```json
{
  "code": 409,
  "message": "所选技师不具备安装服务能力",
  "data": null,
  "request_id": "xxxx"
}
```

## 21. 前端接入要点

1. 列表页状态文案用 `display_status_text`，按钮判断用 `task_status`。
2. 详情页按钮优先用 `can_assign/can_reassign/can_submit_review`。
3. “待执行”不是唯一状态，`pending_assign` 显示“分配师傅”，`pending_execute` 显示“重新分派”。
4. 进度追踪直接渲染 `progress_tracks`。
5. 多环节任务分配优先用 `GET /technicians/available/grouped`。
6. 多环节提交分配建议用 `assignments` 一次提交。
7. `reassign` 支持整单、单环节和批量重派；顶层 `service_type` 修改整单类型，环节重派必须使用 `service_item_id`。
8. 上传接口返回的 `file_url` 已是 `/uploads/...`，前端不要再自行拼接。
9. 师傅端同一任务多环节拆分后，开始执行、上传实据、提交任务建议传 `service_item_id` 或 `execution_id`。
