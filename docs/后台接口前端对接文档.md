# 后台接口前端对接文档

## 1. 说明

这份文档给前端直接对接使用，聚焦本轮已修复和已确认的后台接口问题。

优先规则：

1. 新接入请优先使用本文档中的标准字段
2. 旧页面可继续使用兼容字段
3. 导出类接口返回文件流，不走普通 JSON 列表渲染

## 2. 任务环节枚举

| 值 | 中文 |
| --- | --- |
| `measure` | 量尺 |
| `install` | 安装 |
| `ironing` | 熨烫 |
| `cleaning` | 除尘除螨 |

## 3. 经销商端任务状态说明

涉及页面：

1. 任务列表
2. 任务详情
3. 分配任务页

状态说明：

| 内部状态 | 页面文案 | 说明 |
| --- | --- | --- |
| `pending_assign` | 待执行 | 还未分配师傅，可进入分配任务页 |
| `pending_execute` | 待执行 | 已分配师傅，待师傅开始执行 |
| `executing` | 进行中 | 师傅已开始执行 |

前端判断字段：

| 字段 | 说明 |
| --- | --- |
| `can_assign` | `true` 表示当前任务可分配，进入分配任务页 |
| `can_reassign` | `true` 表示当前任务可重派 |

进度追踪说明：

1. `pending_assign` 时，进度追踪全部可置灰
2. `pending_execute` 时，任务已分派节点会点亮并带时间，其余节点可置灰
3. `executing` 后，才会逐步出现到达现场、现场照片、完成环节的时间
4. 分配任务页对应的任务状态是 `pending_assign`

## 4. 任务列表导出

- 接口：`GET /tasks/export`
- 用途：后台任务列表批量导出
- 查询参数：与 `GET /tasks` 完全一致
- 返回类型：`text/csv`

前端处理：

1. 按文件流下载处理
2. 文件名：`tasks-export.csv`

导出列：

| 字段 | 说明 |
| --- | --- |
| `task_id` | 任务 ID |
| `task_no` | 任务号 |
| `service_type` | 主服务环节 |
| `service_items` | 多环节中文组合 |
| `task_status` | 任务状态中文 |
| `display_status` | 页面状态中文 |
| `review_status` | 评价状态中文 |
| `score_status` | 评分状态中文 |
| `appointment_time` | 预约时间 |
| `customer_name` | 客户姓名 |
| `customer_mobile` | 客户手机号 |
| `store_name` | 门店名称 |
| `dealer_name` | 经销商名称 |
| `technician_name` | 师傅姓名 |
| `technician_mobile` | 师傅手机号 |
| `is_overdue` | 是否逾期，值为 `是/否` |
| `task_tags` | 标签，`|` 拼接 |

## 6. 附件批量下载

- 接口：`POST /attachments/batch-download`
- 用途：批量下载附件
- 返回类型：`application/zip`

标准请求：

```json
{
  "attachment_ids": [1, 2, 3]
}
```

前端处理：

1. 按 zip 文件流下载处理
2. 文件名：`attachments-batch.zip`

## 7. 用户批量删除

- 接口：`POST /users/batch-delete`

标准请求：

```json
{
  "user_ids": [6, 7]
}
```

兼容旧请求：

```json
{
  "ids": ["6", "7"]
}
```

说明：

1. 新页面请使用 `user_ids`
2. 老页面继续传 `ids` 也可用
3. `ids` 支持字符串数组和数字数组

## 8. 技师新增

- 接口：`POST /technicians`

推荐请求：

```json
{
  "name": "陈师傅",
  "mobile": "12364565245",
  "password": "123456",
  "store_id": 23,
  "service_types": ["install", "ironing"]
}
```

兼容旧请求：

```json
{
  "name": "陈师傅",
  "mobile": "12364565245",
  "store_ids": [23],
  "role_names": ["安装", "熨烫"]
}
```

兼容规则：

1. `password` 允许不传，不传默认 `123456`
2. `store_ids` 会兼容为 `store_id`，取第一个值
3. `role_names` 会兼容为 `service_types`
4. `service_types/role_names` 支持中英文混传

服务能力映射：

| 前端可传值 | 后端标准值 |
| --- | --- |
| `量尺` / `measure` | `measure` |
| `安装` / `install` | `install` |
| `熨烫` / `ironing` | `ironing` |
| `除尘除螨` / `cleaning` | `cleaning` |

## 9. 门店信息维护

涉及接口：

1. `GET /stores/{id}`
2. `PATCH /stores/{id}`
3. `POST /stores`
4. `PATCH /stores/{id}/status`

说明：

1. 经销商端门店信息页可直接用这两个接口
2. 后台门店维护页可使用 `GET /stores`、`POST /stores`、`PATCH /stores/{id}`、`PATCH /stores/{id}/status`
3. `POST /stores`、`PATCH /stores/{id}/status` 仅后台管理角色可用

修改请求：

```json
{
  "store_name": "杭州西湖门店",
  "address": "文一路123号",
  "business_hours": "09:00-18:00",
  "contact_name": "张店长",
  "contact_mobile": "13800000000"
}
```

后台新增门店请求：

```json
{
  "store_name": "杭州西湖门店",
  "address": "文一路123号",
  "business_hours": "09:00-18:00",
  "contact_name": "张店长",
  "contact_mobile": "13800000000"
}
```

门店启停用请求：

```json
{
  "status": "disabled"
}
```

## 11. 客户模糊查询

- 接口：`GET /customers`
- 用途：客户管理列表页模糊查询

支持查询参数：

| 字段 | 说明 |
| --- | --- |
| `mobile` | 按手机号模糊匹配 |
| `name` | 按客户姓名模糊匹配 |

示例：

1. `GET /customers?mobile=138`
2. `GET /customers?name=张`

补充说明：

1. `GET /customers/search-by-mobile` 是建单页按完整手机号查客户
2. 客户管理页模糊查询请用 `GET /customers`

## 12. 客户接口新增字段

涉及接口：

1. `GET /customers`
2. `GET /customers/{id}`
3. `GET /customers/search-by-mobile`

新增返回字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `primary_store_id` | number | 主门店 ID |
| `primary_store_name` | string | 主门店名称 |
| `store_ids` | number[] | 关联门店 ID 列表 |

说明：

1. `primary_store_id` 是客户持久化字段
2. `store_ids` 不是客户表直接字段
3. `store_ids`、`store_names` 都是按客户历史任务反查得到
4. 新增/编辑客户时可传 `primary_store_id`

## 13. 协议默认内容

涉及接口：

1. `GET /system/agreements/user`
2. `GET /system/agreements/privacy`

前端约定：

1. 接口现在一定会返回 `content`
2. 即使数据库没有配置，也会返回后端内置默认文本
3. 前端不需要再额外兜底空文案

## 14. 去评分接口

- 接口：`POST /tasks/{id}/hq-score`
- 用途：总部对任务评分

请求结构：

```json
{
  "items": [
    {
      "service_type": "install",
      "score": 90,
      "deduction_reason": ""
    }
  ],
  "score_remark": "总部检核通过"
}
```

说明：

1. `items` 不能为空
2. `score` 范围 `0-100`
3. `service_type` 必须和任务真实环节一致

## 15. 评分导入

- 接口：`POST /hq/scores/import`
- 支持：`csv/xlsx`

导入列：

| 字段 | 说明 |
| --- | --- |
| `task_id` | 任务 ID |
| `service_type` | 服务环节 |
| `score` | 分值 |
| `deduction_reason` | 扣分原因，可空 |
| `score_remark` | 评分备注，可空 |

后端校验：

1. 任务必须存在
2. 任务状态必须是 `pending_hq_score`
3. 同一任务不能重复评分
4. `service_type` 必须属于该任务真实环节
5. 成功后任务状态更新为 `completed`

## 16. 前端建议使用的标准字段

为避免后续再次出现兼容问题，新页面建议统一使用：

1. 批量删除传 `user_ids`
2. 技师新增传 `store_id`
3. 技师新增传 `service_types`
4. 服务能力统一传标准值：`measure/install/ironing/cleaning`
