## 适用范围

本说明只覆盖最近联调变更：

- 同手机号多角色账号与角色切换
- 后台任务详情里的任务环节记录展示
- 任务列表批量下载附件

所有接口默认都挂在 `/api` 下。

## 1. 同手机号多角色与角色切换

### 当前后端能力

- 同一个手机号可以复用同一个账号追加多个角色
- 当前已支持经销商/师傅共用同一个手机号
- 登录、刷新 token、`/auth/me` 都会返回当前激活角色
- 切换角色后，后端权限也会按当前激活角色生效

### 登录返回关键字段

登录接口：

- `POST /auth/login/password`
- `POST /auth/login/code`

返回的 `user` 里重点看：

```json
{
  "roles": ["dealer", "technician"],
  "current_role": "dealer",
  "switchable": true
}
```

字段说明：

- `roles`: 当前账号拥有的全部角色
- `current_role`: 当前激活角色
- `switchable`: 是否显示角色切换入口，等于 `roles.length > 1`

### 前端接法

1. 登录成功后保存：
- `access_token`
- `refresh_token`
- `user.roles`
- `user.current_role`
- `user.switchable`

2. 当 `switchable = true` 时显示角色切换入口。

3. 切换角色调用：

```http
POST /auth/switch-role
Authorization: Bearer <access_token>
Content-Type: application/json

{
  "role_code": "technician"
}
```

4. 切换成功后用返回的新登录态整体覆盖本地：
- `access_token`
- `refresh_token`
- `user.current_role`
- `user.roles`

5. 页面刷新后重新调用：

```http
GET /auth/me
```

返回的 `current_role` 会保持切换后的角色，不会再回到默认角色。

## 2. 后台任务环节记录

### 重点结论

- 后台“任务环节记录”主数据应从任务详情接口拿
- 师傅上传的现场图片不是普通 `attachments` 主来源
- 环节记录的图片优先展示 `progress_tracks[].images`
- 如果要看某一个具体服务环节，前端必须带 `service_item_id`

### 详情接口

任务详情：

```http
GET /tasks/{taskId}
```

查看单个环节详情：

```http
GET /tasks/{taskId}?service_item_id={serviceItemId}
```

也支持：

```http
GET /tasks/{taskId}?service_type=install
```

但前端优先传 `service_item_id`，更准确。

### 前端应使用的字段

任务详情返回里重点用这几个字段：

#### 1. `service_items`

用于渲染任务包含的服务环节列表，例如：

- 量尺
- 安装
- 熨烫
- 除尘除螨

每项字段：

```json
{
  "id": 11,
  "service_type": "install",
  "service_status": "executing",
  "technician_id": 23,
  "scheduled_time": "2026-05-14 15:46:00",
  "started_at": "2026-05-14 16:00:00",
  "completed_at": null,
  "progress_percent": 60,
  "sort_no": 2,
  "is_overdue": false
}
```

推荐前端用法：

- 上方 tabs / 环节切换条：用 `service_items`
- 用户点击某个环节后，重新请求 `GET /tasks/{taskId}?service_item_id={id}`

#### 2. `progress_tracks`

这是“任务环节记录”页最应该直接渲染的字段。

结构示例：

```json
[
  {
    "key": "created",
    "title": "任务创建",
    "finished": true,
    "time": "2026-05-14 15:00:00",
    "expected_time": null,
    "service_type": null,
    "technician_id": null,
    "technician_name": null,
    "images": []
  },
  {
    "key": "photos",
    "title": "现场照片",
    "finished": true,
    "time": "2026-05-14 16:10:00",
    "service_type": "install",
    "technician_id": 23,
    "technician_name": null,
    "images": [
      {
        "id": 201,
        "file_name": "1.jpg",
        "file_url": "/uploads/evidences/images/xxx.jpg"
      }
    ]
  }
]
```

前端建议：

- 时间线：直接渲染 `progress_tracks`
- 照片区：优先取 `progress_tracks` 中 `key === "photos"` 的 `images`

示例逻辑：

```ts
const photoTrack = detail.progress_tracks.find(item => item.key === 'photos')
const images = photoTrack?.images ?? []
```

#### 3. `evidence_items`

这是任务下全部检核图片/视频的兜底列表。

结构：

```json
{
  "id": 201,
  "evidence_type": "image",
  "file_name": "1.jpg",
  "file_url": "/uploads/evidences/images/xxx.jpg",
  "created_at": "2026-05-14 16:10:00"
}
```

推荐前端用途：

- 当 `progress_tracks` 的照片为空时，用它做兜底展示
- 可过滤 `evidence_type === "image"`

### 不要混淆 attachments 和 evidences

#### 普通附件

```http
GET /tasks/{taskId}/attachments
```

用途：

- 任务附件
- 补充文件
- 不是“师傅现场检核图”的主来源

#### 师傅现场图片/视频

```http
GET /tasks/{taskId}/evidences
```

用途：

- 师傅执行环节上传的图片/视频
- 任务环节记录页展示内容的原始来源

### 前端页面建议

后台“任务环节记录”页建议这样接：

1. 首次进入任务详情：

```http
GET /tasks/{taskId}
```

2. 渲染环节 tabs：
- 数据来源 `service_items`

3. 用户点击某个环节后：

```http
GET /tasks/{taskId}?service_item_id={当前环节id}
```

4. 渲染记录内容：
- 时间线：`progress_tracks`
- 现场图片：`progress_tracks[].images`
- 兜底图片列表：`evidence_items`

### 客户评价链接入口

客户评价 H5 页面现推荐使用短码入口：

```text
https://service.ryds.cn/mobile/evaluate?code=AB3K9XQ2
```

说明：

- 页面参数名推荐使用 `code`
- 后端评价接口已兼容 `token` 和 `code`
- 前端可直接把 `code` 当作原来的 `token` 使用

## 3. 任务列表批量下载附件

### 接口

```http
POST /attachments/batch-download
Authorization: Bearer <token>
```

### 当前推荐请求体

任务列表页勾选的是任务行，直接传 `task_ids`：

```json
{
  "task_ids": [1, 2, 3]
}
```

接口仍兼容旧写法：

```json
{
  "attachment_ids": [101, 102, 103]
}
```

### 返回

- 返回 zip 文件流
- 下载文件名为动态名称：
  - `task-attachments-YYYYMMDD-HHMMSS.zip`
  - 或 `attachments-YYYYMMDD-HHMMSS.zip`

### 前端交互约定

#### 1. 未勾选任务

前端直接拦截提示：

```text
请先勾选要下载附件的任务
```

#### 2. 勾选了任务但没有附件

后端会返回错误消息：

```text
所选任务暂无附件
```

前端直接提示这个 message 即可。

### 前端调用示例

```ts
request.post('/api/attachments/batch-download', {
  task_ids: selectedRowKeys,
}, {
  responseType: 'blob',
})
```

## 4. 本次联调前端最小改动清单

### 登录/角色切换

- 登录后保存 `user.current_role`
- 有 `user.switchable` 时显示角色切换入口
- 切角色调用 `POST /auth/switch-role`
- 切完后用新 token 覆盖本地登录态

### 后台任务环节记录

- 环节切换 UI 基于 `service_items`
- 查看某个环节时，请求 `GET /tasks/{taskId}?service_item_id={id}`
- 时间线渲染 `progress_tracks`
- 图片优先渲染 `progress_tracks[].images`
- `evidence_items` 仅做兜底

### 批量下载附件

- 勾选任务后调用 `POST /attachments/batch-download`
- 传 `{ task_ids: selectedRowKeys }`
- 未勾选时提示 `请先勾选要下载附件的任务`
- 若后端返回 `所选任务暂无附件`，直接提示用户
