# 多服务环节任务拆分联调说明

本文档说明“同一任务多个服务环节分配给同一师傅时，师傅端需要按服务环节拆成多条任务卡片”的后端改动和前端接入方式。

## 1. 背景

之前后端师傅端任务列表按 `task.current_technician_id` 查询任务主单，所以同一任务即使包含多个服务环节，也只会在师傅端显示一条任务。

现在已改为按 `task_service_item` 拆分：

1. 一个任务可以包含多个服务环节，例如 `install`、`ironing`。
2. 如果两个服务环节都分配给李师傅，李师傅端任务列表会看到两条任务卡片。
3. 两条任务卡片的任务主单 ID 相同，但 `service_item_id` 和 `service_type` 不同。

## 2. 数据库迁移

已新增并执行迁移：

```text
migrations/0013_task_execution_service_item.sql
```

新增字段：

| 表 | 字段 | 说明 |
| --- | --- | --- |
| `task_execution` | `service_item_id` | 服务环节子项 ID |
| `task_execution` | `service_type` | 服务环节类型 |

新增索引：

| 索引 | 字段 |
| --- | --- |
| `idx_task_execution_service_item_id` | `service_item_id` |
| `idx_task_execution_task_service` | `task_id, service_type` |

线上迁移已验证通过。

## 3. 师傅端任务列表

- 接口：`GET /api/tasks`
- 适用端：师傅端

### 3.1 返回规则

师傅端现在按服务环节返回任务卡片。

例如一个任务有两个环节：

```json
[
  { "service_type": "install", "technician_id": 28 },
  { "service_type": "ironing", "technician_id": 28 }
]
```

师傅 `28` 调用 `GET /api/tasks` 时，会返回两条任务卡片。

### 3.2 关键字段

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | number | 任务主单 ID |
| `service_item_id` | number | 服务环节子项 ID |
| `task_no` | string | 任务编号 |
| `service_type` | string | 当前任务卡片对应的服务环节 |
| `service_status` | string | 当前服务环节状态 |
| `service_items_text` | string | 当前卡片服务环节中文文案 |
| `task_status` | string | 当前卡片状态，师傅端按环节状态展示 |
| `display_status_text` | string | 页面展示状态中文 |
| `customer_name` | string | 客户姓名 |
| `customer_mobile` | string | 客户手机号 |
| `address` | string | 服务地址 |
| `progress_percent` | number | 当前环节进度 |

### 3.3 前端列表 key

前端列表不要只用 `id` 作为唯一 key。

推荐：

```ts
const rowKey = `${item.id}-${item.service_item_id ?? item.service_type}`;
```

## 4. 任务详情

- 接口：`GET /api/tasks/{id}`

### 4.1 查询某个服务环节详情

推荐带 `service_item_id`：

```http
GET /api/tasks/1001?service_item_id=101
```

也支持用 `service_type`：

```http
GET /api/tasks/1001?service_type=install
```

### 4.2 返回规则

师傅端带 `service_item_id` 查询详情时：

1. `service_items` 只返回当前服务环节。
2. `progress_tracks` 按当前服务环节生成。
3. `technician` 返回当前环节师傅。

如果不带 `service_item_id`，后端会尽量按当前师傅的服务环节过滤；如果同一任务有多个环节都属于当前师傅，前端仍建议显式传 `service_item_id`。

## 5. 开始执行

- 接口：`POST /api/tasks/{id}/start`

推荐请求：

```json
{
  "confirm_standard_read": true,
  "service_item_id": 101
}
```

也支持：

```json
{
  "confirm_standard_read": true,
  "service_type": "install"
}
```

成功返回：

```json
{
  "task_id": 1001,
  "task_status": "executing",
  "service_item_id": 101,
  "service_type": "install",
  "execution_id": 501
}
```

前端需要保存 `execution_id`，后续上传实据和提交任务建议使用它。

## 6. 上传实据

### 6.1 上传图片

- 接口：`POST /api/tasks/{id}/evidences/images`
- 请求类型：`multipart/form-data`

推荐带 `execution_id`：

```http
POST /api/tasks/1001/evidences/images?execution_id=501
```

也支持：

```http
POST /api/tasks/1001/evidences/images?service_item_id=101
```

### 6.2 上传视频

- 接口：`POST /api/tasks/{id}/evidences/videos`

参数规则同图片上传。

### 6.3 说明

1. 图片数量限制按 `execution_id` 单独计算。
2. 多个服务环节不会互相占用图片数量。
3. 如果同一任务多个服务环节都在执行中，上传时必须带 `execution_id` 或 `service_item_id`，避免后端无法判断上传到哪个环节。

## 7. 提交任务

- 接口：`POST /api/tasks/{id}/submit`

推荐请求：

```json
{
  "execution_id": 501,
  "service_item_id": 101,
  "submit_remark": "安装完成"
}
```

也支持：

```json
{
  "execution_id": 501,
  "service_type": "install",
  "submit_remark": "安装完成"
}
```

成功返回：

```json
{
  "task_id": 1001,
  "task_status": "executing",
  "service_item_id": 101,
  "service_type": "install",
  "execution_id": 501
}
```

状态规则：

1. 只提交当前服务环节，不会把同任务其他环节一起提交。
2. 如果还有其他服务环节未提交，任务主状态保持 `executing`，但已提交环节在经销商端会按单独卡片显示为 `pending_dealer_review`。
3. 当所有服务环节都提交后，任务主状态变为 `pending_dealer_review`。
4. 经销商评价按 `service_item_id` 单环节提交；所有服务环节都评价后，任务主状态才进入 `pending_hq_score`。
5. 经销商端待评价通知仍在全部环节提交后发送。

## 8. 分配通知

多服务环节分配现在按服务环节发送通知。

例如：

```json
[
  { "service_type": "install", "technician_id": 28 },
  { "service_type": "ironing", "technician_id": 28 }
]
```

师傅 `28` 会收到两条通知：

1. 安装任务待执行
2. 熨烫任务待执行

## 9. 前端改造要点

1. 师傅端和经销商端任务列表都必须按 `id + service_item_id` 作为唯一任务卡片。
2. 点击任务卡片进入详情时，带上 `service_item_id`。
3. 开始执行时传 `service_item_id`。
4. 上传实据时优先传 `execution_id`。
5. 提交任务时传 `execution_id`，建议同时传 `service_item_id`。
6. 经销商评价时传当前卡片的 `service_item_id`。
7. 不要再假设一个任务主单只会在师傅端或经销商端出现一次。

## 10. 兼容说明

旧单环节任务仍兼容：

1. 如果没有 `task_service_item`，仍按任务主单处理。
2. 旧请求不传 `service_item_id` 时，在只有一个可操作环节的情况下仍可用。
3. 如果同一任务存在多个可操作环节，不传 `service_item_id/service_type` 会返回错误，要求前端明确指定环节。
