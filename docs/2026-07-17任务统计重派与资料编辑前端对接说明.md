# 近期后端修改前端对接说明

本文只汇总本次最新修改，供管理端和小程序前端联调：

1. 任务列表全量统计
2. 任务重新分派并同步修改任务资料
3. 门店新增与编辑校验
4. 师傅编辑原子保存

所有接口统一使用 `/api` 前缀，并携带：

```http
Authorization: Bearer <access_token>
Content-Type: application/json
```

成功响应统一为：

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "request_id": "uuid"
}
```

常用错误对应关系：

| HTTP | `code` | 前端处理 |
| --- | ---: | --- |
| 400 | 1001 | 展示字段校验信息 |
| 401 | 1006 | 登录失效，刷新 token 或重新登录 |
| 403 | 1007 | 提示无权限，不清除登录态 |
| 404 | 2001 | 提示数据不存在并刷新列表 |
| 409 | 2002 | 提示业务或并发冲突，并重新获取详情 |
| 500 | 9000 | 提示稍后重试，保留 `request_id` 便于排查 |

前端业务判断应使用 HTTP 状态和 `code`，不要依赖中文 `message`。

## 1. 任务列表全量统计

### 1.1 接口

```http
GET /api/tasks?page=1&page_size=10
```

筛选参数保持不变，常用字段如下：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `task_no` | string | 任务编号 |
| `service_type` | string | 服务环节 |
| `task_type` | string | `three_special` / `four_special` |
| `task_status` | string | 任务状态 |
| `review_status` | string | 评价状态 |
| `score_status` | string | `pending` / `scored` |
| `store_id` | number | 门店 ID |
| `technician_id` | number | 师傅 ID |
| `appointment_start` | string | 开始时间，`YYYY-MM-DD HH:mm:ss` |
| `appointment_end` | string | 结束时间，`YYYY-MM-DD HH:mm:ss` |
| `mobile` | string | 客户手机号 |
| `customer_name` | string | 客户姓名 |
| `page` | number | 默认 1 |
| `page_size` | number | 默认 20 |

新页面建议统一使用 snake_case。后端仍兼容 `taskNo`、`serviceType`、`taskStatus`、`storeId`、`technicianId`、`customerMobile` 等旧字段。

### 1.2 返回结构

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "items": [],
    "total": 43,
    "summary": {
      "pending_execute": 18,
      "executing": 4,
      "pending_review": 9,
      "completed": 12
    },
    "page": 1,
    "page_size": 10
  },
  "request_id": "uuid"
}
```

本次修复后的统计口径：

- `items` 只包含当前页。
- `total` 是当前角色数据范围及全部筛选条件生效后、分页前的总行数。
- `summary` 与 `total` 基于同一批分页前数据计算。
- `summary` 四项之和等于 `total`。
- 当前查询中的 `task_status` 等条件也会影响 `summary`，它不是忽略筛选条件的全局看板。
- 经销商端和师傅端的多环节任务可能拆成多行，统计单位与列表展示行一致；同一 `id` 可以对应不同 `service_item_id`。

顶部统计卡片必须按以下字段绑定：

| 卡片 | 数据字段 |
| --- | --- |
| 全部 | `data.total` |
| 待执行 | `data.summary.pending_execute` |
| 进行中 | `data.summary.executing` |
| 待评价 | `data.summary.pending_review` |
| 已完成 | `data.summary.completed` |

禁止使用 `data.items.length` 或对当前页 `items` 做 `reduce` 计算顶部统计。

状态聚合规则：

| 原任务状态 | `display_status` | 统计字段 |
| --- | --- | --- |
| `pending_assign` / `pending_execute` | `pending_execute` | `pending_execute` |
| `executing` | `executing` | `executing` |
| `pending_dealer_review` | `pending_review` | `pending_review` |
| `completed` / `closed` / 旧 `pending_hq_score` | `completed` | `completed` |

前端接入示例：

```ts
const data = response.data.data;

tableRows.value = data.items;
pagination.total = data.total;

cards.value = {
  all: data.total,
  pendingExecute: data.summary.pending_execute,
  executing: data.summary.executing,
  pendingReview: data.summary.pending_review,
  completed: data.summary.completed,
};
```

筛选、重置、翻页、重派成功后，都应重新请求该接口。后端已经完成排序，前端不要再次按 ID 重排。

## 2. 任务重新分派

### 2.1 接口与使用条件

```http
POST /api/tasks/{id}/reassign
```

允许角色：`dealer`、`hq_reviewer`、`super_admin`。经销商只能操作所属门店任务。

允许任务状态：

- `pending_execute`
- `executing`

本次已取消“新师傅不能与当前师傅相同”的限制。前端师傅下拉框不要禁用当前师傅；任务资料发生变化但师傅不变时，也可以选择当前师傅重新派发。

重派接口现在直接复用正常分派的参数结构，支持整单、单环节和多环节批量重派。

### 2.2 请求字段

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `technician_id` | number | 条件必填 | 整单或单环节重派的目标师傅 ID，可以等于当前师傅 ID |
| `service_item_id` | number | 否 | 单环节重派 ID；传入即进入单环节模式 |
| `service_type` | string | 否 | 整单重派的新任务类型；未传保留原类型，只支持 `measure/install/ironing/cleaning` |
| `assignments` | object[] | 否 | 多环节批量重派；每项必须传 `technician_id + service_item_id` |
| `assign_reason` | string | 否 | 重派原因；未传、传 `null` 或空字符串时默认“重新分派” |

模式判定规则：

| 请求内容 | 执行模式 |
| --- | --- |
| 不传 `service_item_id`、`assignments`；可传 `technician_id + service_type` | 整单重派，顶层 `service_type` 修改任务本身 |
| 传 `technician_id + service_item_id` | 单环节重派；可选 `service_type` 只校验 ID 一致性 |
| 传非空 `assignments` | 多环节批量重派 |

前端不要混用三种模式。传 `assignments` 时必须省略顶层 `technician_id/service_item_id/service_type`；`assignments` 不能为空，每项必须传 `service_item_id`，且同一个服务环节不能重复出现。

#### 整单重派

最简请求与正常整单分派一致：

```json
{
  "technician_id": 29
}
```

需要记录原因时可传：

```json
{
  "technician_id": 29,
  "assign_reason": "客户调整服务时间"
}
```

修改当前任务服务类型并重新分派：

```json
{
  "technician_id": 29,
  "service_type": "install",
  "assign_reason": "由量尺任务调整为安装任务"
}
```

#### 单环节重派

优先使用 `service_item_id`：

```json
{
  "technician_id": 29,
  "service_item_id": 101,
  "assign_reason": "安装环节更换师傅"
}
```

单环节重派必须使用详情返回的 `service_items[].id`，不能只传 `service_type`。

#### 多环节批量重派

```json
{
  "assignments": [
    {
      "service_item_id": 101,
      "technician_id": 29
    },
    {
      "service_item_id": 102,
      "service_type": "ironing",
      "technician_id": 35
    }
  ],
  "assign_reason": "按服务能力重新安排"
}
```

`service_item_id` 必须属于当前任务或同一任务组，使用对应任务详情中 `service_items[].id` 的返回值。批量项中的 `service_type` 仅作一致性校验，可省略。

### 2.3 整单重派时可选的资料字段

以下扩展字段继续兼容，但只允许在整单重派时提交：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `customer_name` | string | 否 | 修改共享客户姓名；传入时不能为空 |
| `customer_mobile` | string | 否 | 修改共享客户手机号；传入时不能为空且必须唯一 |
| `customer_source` | string | 否 | 修改客户来源 |
| `address_id` | number | 否 | 选择当前客户已有地址 |
| `address` | string/object | 否 | 新服务地址，优先级高于 `address_id` |
| `appointment_time` | string | 否 | `YYYY-MM-DD HH:mm:ss` |
| `service_time_slot` | string | 否 | 服务时段 |
| `priority` | string | 否 | 建议使用 `low` / `normal` / `high` |
| `task_desc` | string | 否 | 任务描述 |
| `task_remark` | string | 否 | 任务备注 |

整单重派并修改资料示例：

```json
{
  "technician_id": 29,
  "service_type": "install",
  "assign_reason": "任务资料调整后重新派发",
  "customer_name": "张三",
  "customer_mobile": "13800000000",
  "customer_source": "门店到访",
  "appointment_time": "2026-07-18 14:30:00",
  "service_time_slot": "下午",
  "address": {
    "province": "浙江省",
    "city": "杭州市",
    "district": "西湖区",
    "detail": "文一路 123 号"
  },
  "priority": "normal",
  "task_desc": "更新后的任务描述",
  "task_remark": "更新后的备注"
}
```

地址也可以直接传字符串：

```json
{
  "technician_id": 29,
  "assign_reason": "修改服务地址",
  "address": "浙江省杭州市西湖区文一路 123 号"
}
```

按单环节或 `assignments` 批量重派时，不得同时提交上述任一资料字段。需要同时调整资料和环节师傅时，前端应先整单提交资料，再单独发起按环节重派；否则接口返回 400。

### 2.4 兼容字段

兼容旧页面的字段包括：

| 标准字段 | 兼容字段 |
| --- | --- |
| `technician_id` | `technicianId` |
| `service_item_id` | `serviceItemId` |
| `service_type` | `serviceType` |
| `assign_reason` | `assignReason` |
| `customer_name` | `customerName`、`name`、`customer.name` |
| `customer_mobile` | `customerMobile`、`mobile`、`phone`、`customer.mobile` |
| `customer_source` | `customerSource` |
| `address_id` | `addressId` |
| `address` | `customer_address`、`service_address`、`customer.address` |
| `appointment_time` | `appointmentTime` |
| `service_time_slot` | `serviceTimeSlot` |
| `task_desc` | `taskDesc` |
| `task_remark` | `taskRemark` |

`assignments[]` 子项同样兼容 `serviceItemId`、`serviceType`、`technicianId`。首次分派与重新分派使用同一套字段名和别名，但顶层 `service_type` 的模式语义不同：首次分派可用于定位环节，重新分派用于修改整单类型。

新页面只发送一套标准字段，不要在同一个请求中混传同义字段。

### 2.5 资料字段保存规则

该接口与门店/师傅 PATCH 的三态规则不同：

- 可选字段未传：保留原值。
- 可选字段传 `null`：等同未传，仍保留原值。
- `service_type` 传空白或非法值：返回 400；不修改类型时请省略或传 `null`。
- `customer_name`、`customer_mobile` 传空字符串：返回 400。
- `appointment_time` 传空字符串或格式错误：返回 400。
- `address.detail` 为空：返回 400。
- 如需清空 `task_desc`、`task_remark` 等普通文本，可明确传空字符串。

重派成功后重新请求 `GET /api/tasks/{id}` 时，详情会通过 `customer_source`、`address_id` 和 `customer.source/customer.address_id` 回传对应资料。显式保存过 `service_time_slot` 时详情优先返回该原值；未保存时才根据 `appointment_time` 返回 `HH:mm`。详情查询参数同时兼容 `service_item_id/service_type` 与 `serviceItemId/serviceType`。

客户姓名、手机号、来源属于共享客户资料，修改后该客户的其他历史任务也会显示新资料。客户手机号与其他客户重复时返回 `409 / 2002`。

地址规则：

- 仅传 `address_id` 时，该地址必须属于当前客户。
- 传入新 `address` 时，后端创建一条非默认客户地址，并把当前任务切换到新地址。
- 新地址不会覆盖或删除历史地址。
- `address` 和 `address_id` 同时传时，以 `address` 为准。

### 2.6 重派后的状态变化

整单重派：

- 任务主状态重置为 `pending_execute`。
- 显式传 `service_type` 时，同步更新任务主表和唯一服务环节；必须恰好存在 1 个服务环节。
- 新师傅按新 `service_type` 校验服务能力；同组已有目标类型时返回 409。
- 所有服务环节统一分给目标师傅。
- 所有服务环节状态重置为 `pending_execute`。
- 服务环节进度重置为 0。
- `started_at`、`completed_at` 被清空。
- 修改预约时间时，各服务环节 `scheduled_time` 同步为新时间。
- 未修改预约时间时，各服务环节保留原 `scheduled_time`。
- 进行中的旧执行记录会变为 `cancelled`，旧 `execution_id` 不能继续提交。
- 已取消执行的历史照片和定位保留在详情历史中，但不再计入当前进度。
- 即使仍选择当前师傅，也会产生新的重派记录、重置执行状态并重新通知师傅。

单环节或批量重派：

- 只重置选中的服务环节，未选中的环节、进度和师傅保持不变。
- 只取消选中环节正在进行的旧执行记录。
- 选中环节状态重置为 `pending_execute`，进度重置为 0，并清空 `started_at`、`completed_at`。
- 如其他环节仍在执行，任务主状态保持 `executing`；否则回到 `pending_execute`。
- 每个选中环节分别校验目标师傅的所属门店和服务能力，并分别发送通知。

整单或按环节重派都在事务中保存。任一步失败都会整体回滚，不会出现部分环节或部分资料已经修改的情况。

以下情况会拒绝重派：

- 当前任务不是 `pending_execute` 或 `executing`。
- 整单重派时，任一服务环节已经提交检核、待评价或完成。
- 按环节重派时，选中环节不是 `pending_execute` 或 `executing`。
- 整单存在已提交执行记录，或选中环节存在 `submitted` 执行记录。
- 当前客户已删除。
- 目标师傅被删除或禁用。
- 目标师傅不属于当前任务门店。
- 目标师傅缺少任务所需的任一服务能力。
- 任务或客户已被其他操作并发修改。

状态、执行记录、师傅资格或并发冲突通常返回 409；缺少目标师傅、环节不存在、环节重复、空 `assignments` 或按环节夹带资料返回 400。

### 2.7 成功响应与前端处理

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "task_id": 1001,
    "task_status": "pending_execute",
    "service_item_id": null,
    "service_type": null,
    "execution_id": null
  },
  "request_id": "uuid"
}
```

一次只重派一个环节时，`service_item_id` 和 `service_type` 返回实际环节；整单或一次重派多个环节时二者为 `null`。`task_status` 以接口实际返回为准，按环节重派后可能仍为 `executing`。

成功后前端必须：

1. 关闭重派弹窗。
2. 清除页面缓存的旧 `execution_id`。
3. 重新请求任务详情。
4. 重新请求任务列表和顶部统计。

不要只在本地替换师傅姓名，因为任务状态、执行记录、资料和多个服务环节都可能同时变化。

## 3. 门店新增与编辑

### 3.1 新增门店

```http
POST /api/stores
```

本次新增校验要求：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `store_name` | 是 | 兼容别名 `name`，不能为空且不能重复 |
| `province` | 是 | 不能为空 |
| `city` | 是 | 不能为空 |
| `district` | 是 | 不能为空 |
| `code` | 否 | 非空时必须唯一 |
| `address` | 否 | 详细地址 |
| `remark` | 否 | 备注 |
| `business_hours` | 否 | 营业时间 |
| `contact_name` | 否 | 门店负责人 |
| `contact_mobile` | 否 | 负责人联系方式 |
| `status` | 否 | 默认 `enabled` |

`status` 支持 `enabled/active` 和 `disabled/inactive`，最终返回 `enabled/disabled`。非法状态不再静默转为启用，而是返回 400。

### 3.2 编辑门店

```http
PATCH /api/stores/{id}
```

编辑接口保留标准 PATCH 三态：

| JSON 表现 | 含义 |
| --- | --- |
| 局部 PATCH 不发送字段 | 保留原值 |
| `"field": null` | 明确清空可选字段；必填字段报错 |
| `"field": value` | 校验并更新 |

为兼容后台门店完整编辑表单，当请求同时包含 `store_name/name`、`province`、`city`、`district` 时，后端按完整表单保存。此模式下，以下表单可选字段即使未发送也表示清空：

- `code`
- `address`
- `remark`
- `contact_name`
- `contact_mobile`

`business_hours` 不在当前后台编辑表单内，未发送时仍保留原值；显式传 `null`、空字符串或纯空格时可清空。

不可清空字段：

- `store_name` / `name`
- `province`
- `city`
- `district`
- `status`

以上字段传 `null`、空字符串或纯空格会返回 400，整次请求不保存。

可显式清空字段：

- `code`
- `address`
- `remark`
- `business_hours`
- `contact_name`
- `contact_mobile`

以上字段传 `null`、空字符串或纯空格都会保存为 `null`。其中除 `business_hours` 外，完整表单模式下未发送也会保存为 `null`。

局部更新时可以只提交发生变化的字段：

```json
{
  "address": "文三路 18 号",
  "contact_name": null,
  "remark": "周末正常营业"
}
```

后台完整编辑表单可以省略已清空的五个表单可选字段。其他局部 PATCH 如需清空字段，仍应发送 `null` 或空字符串。

编辑时，后端会先完成全部必填校验、状态校验、名称和编码唯一性校验，再执行一次更新。因此返回校验错误时，本次提交的其他字段也不会保存。

成功响应的 `data` 为完整门店信息，包含：

```text
id, name, store_name, code, contact_name, contact_mobile,
province, city, district, region_text, address, remark,
business_hours, status, technician_count, customer_count,
completed_task_count, completion_rate
```

前端成功后直接使用响应刷新当前行，或重新请求门店列表。并发编辑同一门店时以后提交结果为准。

常见错误：

| HTTP / code | 场景 |
| --- | --- |
| 400 / 1001 | 名称或省市区为空、状态非法 |
| 403 / 1007 | 经销商编辑非所属门店 |
| 404 / 2001 | 门店不存在 |
| 409 / 2002 | 门店名称或编码重复 |

## 4. 师傅编辑

### 4.1 接口

```http
PATCH /api/technicians/{id}
```

允许角色：`dealer`、`hq_reviewer`、`super_admin`。经销商只能编辑所属门店师傅，并且只能选择自己所属门店。

### 4.2 字段规则

师傅编辑保留“未传 / `null` / 有值”三态，同时兼容后台完整编辑表单：

| 标准字段 | 兼容字段 | 规则 |
| --- | --- | --- |
| `name` | 无 | 最终必填，不可清空 |
| `mobile` | `phone` | 最终必填、唯一，不可清空 |
| `nickname` | 无 | 可清空 |
| `email` | 无 | 可清空 |
| `avatar_url` | `avatarUrl` | 可清空 |
| `id_card` | `idCard` | 可清空；完整表单未传也会清空 |
| `emergency_contact_name` | `emergencyContactName` | 可清空；完整表单未传也会清空 |
| `emergency_contact_mobile` | `emergencyContactMobile` | 可清空；完整表单未传也会清空 |
| `job_no` | `jobNo` | 可清空 |
| `store_id` | `storeId` | 最终必填，必须大于 0 |
| `service_types` | `serviceTypes` | 最终至少一项 |
| `status` | 无 | `null` 非法；未传或空字符串表示保留 |

当请求同时包含 `name`、`mobile/phone`、`store_id/storeId`、`service_types/serviceTypes`、`status` 时，后端将其识别为后台完整编辑表单。此模式下，`id_card`、`emergency_contact_name`、`emergency_contact_mobile` 未传、传 `null`、空字符串或纯空格都会清空。

局部 PATCH 中字段未传仍保留原值。`nickname`、`email`、`avatar_url`、`job_no` 不属于当前后台完整表单，未传始终保留，只有显式传 `null` 或空白才清空。

以下输入会返回 400，并且整次修改不保存：

- `name: null` 或空字符串
- `mobile: null` 或空字符串
- `store_id: null`、0 或不存在的门店
- `service_types: null` 或 `[]`
- `status: null` 或非法状态

服务能力支持：

| 标准值 | 兼容中文 |
| --- | --- |
| `measure` | `量尺` |
| `install` | `安装` |
| `ironing` | `熨烫` |
| `cleaning` | `除尘除螨`、`除尘`、`除螨` |

后端会统一转换为英文值并去重。

状态支持：

- 启用：`enabled`、`active`、`启用`、`已启用`
- 禁用：`disabled`、`inactive`、`禁用`、`已禁用`

后台完整编辑表单应继续发送当前 `status`。局部 PATCH 未修改状态时可以不发送 `status`，不要发送 `null`。

### 4.3 请求示例

修改必填资料和服务能力：

```json
{
  "name": "王浩",
  "mobile": "13900001111",
  "store_id": 12,
  "service_types": ["measure", "install", "cleaning"],
  "status": "enabled"
}
```

完整表单中保留身份证号时必须继续发送 `id_card`。紧急联系人在输入框清空后可直接省略：

```json
{
  "name": "王浩",
  "mobile": "13900001111",
  "id_card": "330100199001011234",
  "store_id": 12,
  "service_types": ["measure", "install"],
  "status": "enabled"
}
```

上述请求会保留 `id_card`，并清空未发送的 `emergency_contact_name`、`emergency_contact_mobile`。

只清空可选字段：

```json
{
  "nickname": null,
  "email": null,
  "emergency_contact_name": ""
}
```

手机号修改只更新师傅业务手机号，不会覆盖同一用户可能存在的独立后台登录字段 `account`。

### 4.4 原子保存与登录影响

后端会在写库前统一校验：

- 姓名和手机号
- 手机号唯一性
- 师傅角色状态
- 所属门店是否存在及当前账号是否有权限选择
- 服务能力是否合法且至少一项

用户资料、师傅身份状态、服务能力、门店绑定和会话版本在同一个事务中提交。任一步失败都会回滚，不会出现“接口报错但部分字段已经保存”。

手机号、状态、服务能力或门店实际变化时，师傅的登录会话版本会更新，已有 token 会失效，师傅需要重新登录。只修改昵称、邮箱等普通资料不会强制下线。

成功响应的 `data` 为完整师傅详情。状态判断必须使用：

| 字段 | 说明 |
| --- | --- |
| `status_code` | `enabled` / `disabled`，用于逻辑判断 |
| `status` | `已启用` / `已禁用`，用于展示 |
| `status_text` | `已启用` / `已禁用`，用于展示 |

响应还包含 `store_ids`、`store_names`、`service_types`、`work_status`、平均分、任务数量、当前任务、最近任务及近六个月趋势。

常见错误：

| HTTP / code | 场景 |
| --- | --- |
| 400 / 1001 | 必填项为空、技能或状态非法、门店不存在 |
| 403 / 1007 | 编辑或选择了非所属门店 |
| 404 / 2001 | 师傅不存在、已删除或师傅角色不存在 |
| 409 / 2002 | 手机号重复、历史门店关系异常或并发修改 |

## 6. 联调验收用例

1. `page_size=10` 且总数大于 10 时，顶部“全部”和分页总数一致，不等于 `items.length`。
2. 带门店、日期、师傅等筛选后，`summary` 四项之和等于 `total`。
3. 重派给当前师傅并修改预约时间，接口成功且任务回到待执行。
4. 重派时修改地址和客户姓名，刷新详情后显示新资料。
5. 重派手机号与其他客户重复时返回 409，任务及客户资料均不变化。
6. 门店必填项清空并同时修改备注时返回 400，备注也不保存。
7. 门店负责人传 `null` 后可正常清空。
8. 师傅技能传空数组并同时修改姓名时返回 400，姓名不保存。
9. 师傅昵称传 `null` 后可清空。
10. 师傅手机号修改成功后，独立后台账号 `account` 不变化，旧师傅 token 失效。

数据库方面，生产环境已应用客户手机号唯一约束；其他联调环境需应用 `migrations/0025_customer_mobile_unique.sql` 后再验证手机号冲突场景。
