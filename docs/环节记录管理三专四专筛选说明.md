# 环节记录管理三专四专筛选说明

## 适用范围

本文说明后台 `环节记录管理` 列表的任务类型筛选。接口默认挂在 `/api` 下。

```http
GET /hq/review/tasks
```

## 对接参数

前端筛选任务类型时传 `task_type`：

```http
GET /hq/review/tasks?task_type=three_special&page=1&page_size=20
GET /hq/review/tasks?task_type=four_special&page=1&page_size=20
```

允许值：

- `three_special`：三专
- `four_special`：四专

## 业务口径

三专、四专不是按单条任务字段硬筛选，而是按同一组任务的实际服务项目数判断。

- 分组字段：`task.task_group_no`
- 三专：同一组内已进入执行后的服务类型数为 `3`
- 四专：同一组内已进入执行后的服务类型数为 `4`

后端统计时会过滤掉待执行项目：

- `task.task_status = pending_execute` 的任务不计入三专/四专数量
- `task_service_item.service_status = pending_execute` 的环节不计入三专/四专数量
- 列表返回时，三专/四专筛选结果里也不会返回待执行环节

后端按 `service_type` 去重统计，避免历史重复环节行导致三专被算成四专。

## 服务类型

当前服务类型顺序如下：

1. `measure`：量尺服务
2. `install`：安装服务
3. `ironing`：熨烫服务
4. `cleaning`：除尘除螨服务

示例：同一 `task_group_no` 下有量尺、安装、除尘除螨已进入执行后，熨烫仍是待执行，则筛选 `three_special` 会返回前三个环节，筛选 `four_special` 不会返回该组。

## 兼容规则

如果历史数据没有 `task_group_no`，后端会兼容旧字段 `task.task_type`：

- `task.task_type = three_special`
- `task.task_type = four_special`

有 `task_group_no` 时，优先按同组非待执行服务类型数判断。

## 前端处理

前端只需要传筛选参数并按返回的 `items` 渲染，不需要再次计算三专/四专，也不需要手动过滤待执行项目。
